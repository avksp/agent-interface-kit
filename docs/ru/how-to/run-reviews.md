# Ревью решений и аудит кода

[English version](../../how-to/run-reviews.md)

## Выбор проверяющего

1. Определите риск ревью. Если в область входят архитектура, безопасность или сложная логика, используйте критический маршрут.
2. Покажите маршрут командой `npm run review:route -- architecture`. Замените `architecture` на предмет ревью. [Политика](../../../config/review-policy.json) задаёт порядок, а её [схема](../../../schemas/review-policy.v1.schema.json) проверяет структуру.
3. Перед запуском подтвердите точные адаптер, модель и уровень рассуждений на текущем хосте. Переходите к следующему варианту только при подтверждённой недоступности предыдущего до запуска. Запишите причину. Таймаут и отрицательный результат остаются в истории ревью.
4. Для управляемого запуска ALK используйте согласованную локальную привязку с теми же моделью и уровнем рассуждений. Привязка требует собственных доказательств поддержки и квалификации. В ARS укажите тот же маршрут в назначении проверяющего. Политика проекта выбирает варианты для обоих инструментов. Запуск и полномочия определяет процесс соответствующего инструмента.

| Ревью | Порядок |
| --- | --- |
| Решение, архитектура, безопасность, сложная логика | Codex · `gpt-6.2-astra` · `high` |
| Остальные аудиты | Qwen Code · `qwen4-max` · `high`, Qwen Code · `deepseek-v4-pro-0813` · `high`, Grok Build · `grok-4.7` · `high`, OpenCode · GLM 5.3 · `max` |
| Простой анализ или аудит | OpenCode · GLM 5.3 · `max` |

Селектор OpenCode — `zai-coding-plan/glm-5.3#max`. В Qwen наличие модели без подтверждённого параметра `high` означает недоступность точного маршрута. Подтвердите действующий уровень рассуждений перед переходом к следующему варианту.

## Ревью решения перед заморозкой

1. Подготовьте пакет только для чтения с точной ревизией черновика, областью, требованиями, критериями проверки и относящимися к ним исходниками или доказательствами реализуемости.
2. Используйте независимую роль `ars-review-solution`. Запросите сравнение с текущим подходом и значимыми альтернативами. Проверьте соответствие требованиям, интеграцию, безопасность, ресурсы, реализуемость и проверяемость.
3. Свяжите запрос и вывод ARS с точным пакетом. Проверьте отчёт по отдельным доверенным ожиданиям вызывающей стороны. Оцените замечания и пробелы до принятия решения.
4. Устраните блокирующие замечания или пересмотрите план. Сохраните отчёт и проверку в `tasks/reviews/`. Зафиксируйте точный пакет и исход ревью.
5. Завершайте ревью плана ALK и заморозку после прохождения ревью решения. Для реализации используйте обычное разрешение ALK.

## Периодический аудит

1. Посчитайте выпущенные релизы после последнего полного аудита. Проведите аудит после трёх релизов, если хотя бы один изменил публичный контракт, конвейер компиляции или границу доверия между слоями. Иначе проведите его после четырёх.
2. Привяжите выпущенную ревизию Git, относящиеся к ней изменения, результаты тестов и воспроизводимый базовый замер быстродействия.
3. Используйте ARS для проверки архитектуры, безопасности, инженерных практик и измеренного быстродействия. Используйте `ars-review-security` для защитного анализа и `ars-review-implementation` для изменений кода и доказательств. Применяйте соответствующий маршрут к каждому предмету.
4. Запишите замечания, пробелы покрытия, исправления и их проверки. Сравнивайте скорость в одинаковых средах. Сохраняйте требования архитектуры и безопасности как условия приёмки.
5. Обнулите счётчик релизов после принятия полного аудита. Сохраняйте предыдущие отчёты и отметки о недоступной телеметрии.
